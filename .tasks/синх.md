# Синхронизация между браузерами и совместное редактирование

Синхронизация состояния деска в реальном времени при работе в разных браузерах/вкладках и при одновременном редактировании несколькими пользователями.

## 1. Текущий контекст системы

- **Сервер:** Express 5 (`server/src/index.ts`), Mongoose (`server/src/models/Node.ts`).
- **Существующая дельта-выборка:** [node.service.ts](file:///d:/_sites/a-node(v.AI)/server/src/services/node.service.ts#L40-L50) уже умеет отдавать только изменившиеся ноды через параметр `?since=<ISO_DATE>` (`lastUpdate > since`), включая удалённые (`inTrash`, `ok`).
- **Клиентское сохранение:** [serverPersistence.ts](file:///d:/_sites/a-node(v.AI)/client/src/features/core/serverPersistence.ts#L122-L147) буферизирует грязные ноды (`dirtyNodes`) с дебаунсом 1000мс и отправляет `PUT /nodes/saveNodes`.
- **Инкрементальное обновление DOM:** [nodeSerialization.ts](file:///d:/_sites/a-node(v.AI)/client/src/features/nodes/nodeSerialization.ts#L50-L159) (`diffDeskSnapshot`) точечно добавляет, удаляет и обновляет ноды без полной перерисовки страницы.

---

## 2. Архитектура решения

### Транспорт: SSE (Server-Sent Events) + Delta REST
- **Почему SSE:** Нативно поддерживается браузером (`EventSource`), автоматический реконнект, не требует сторонних библиотек на сервере/клиенте, идеально сочетается с уже готовым REST API сохранения (`PUT /nodes/saveNodes`).
- **Канал:** `GET /nodes/:deskId/events` (держит стрим для каждого активного деска).
- **Событие сервера:** При успешном `bulkSaveNodes` сервер рассылает подписчикам деска:
  ```json
  { "type": "nodes_updated", "senderId": "clientId", "serverTime": "2026-11-03T08:14:00.000Z" }
  ```
- **Fallback / Офлайн:** Слушатель `visibilitychange` и `focus` для мгновенной проверки изменений при возвращении пользователя во вкладку.

---

## 3. Защита от конфликтов при совместном редактировании

1. **Исключение эха (Sender Suppression):** Клиент передает в заголовке `X-Client-Id: <uuid>`. Сервер не рассылает SSE-уведомление клиенту-инициатору.
2. **Гранулярный Dirty Guard (Per-Node):**
   - Сейчас в `serverPersistence.ts` стоит грубая блокировка: `if (this.dirtyNodes.size === 0)`.
   - Нужно проверять конфликт понодно: если нода находится в `dirtyNodes` или в фокусе инпута (редактируется пользователем), серверные данные для этой конкретной ноды временно откладываются, а остальные ноды деска обновляются беспрепятственно.
3. **Коллизии `lID` (локальные идентификаторы списков):**
   - При создании нод двумя пользователями одновременно `lID` могут пересечься.
   - Механизм [core.ts](file:///d:/_sites/a-node(v.AI)/client/src/features/core/core.ts#L94-L105) уже детектирует дубли `lID` и переназначает их. Дополнить проверку при инкрементальном слиянии.
